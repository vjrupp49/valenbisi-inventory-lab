# Analysis plan: from collected data to defensible results

Written 2026-10-25, when about 15 full days of real data exist (Oct 10 to Oct 24 complete).
This plan covers the "real data" phase. The earlier roadmap in CLAUDE.md built the machinery on synthetic data;
this plan is about pointing it at reality without fooling ourselves.

**Rule for the whole plan:** every number in any doc must come from a script in this repo run on the real data.
Questions below are *questions*, not findings. Things marked "suspect" are hunches to test, not facts.

## How the phases fit together

| Phase | What | Why it comes here | Gate to move on |
|---|---|---|---|
| 0 | Freeze the dataset | Results must be reproducible | Cutoff and data-branch commit recorded |
| 1 | **Data integrity audit** | Everything later depends on knowing what the data can support | Audit report reviewed by Vincent |
| 2 | Analysis charter (can / can't / only-with-caveats) | Turns audit findings into scope decisions | Vincent agrees with the scope |
| 3 | Fix the data layer to match reality | The models must reflect what the audit found | `dbt build` + new real-data tests pass |
| 4 | Descriptive service-level analysis | Safest, most valuable output | Reconciles to raw data |
| 5 | Segmentation (ABC/XYZ) | Needs Phase 3 definitions | Stable under small changes to thresholds |
| 6 | Forecast backtest | Only if Phase 2 says the target is observable | Beats baselines out of sample, or we say it doesn't |
| 7 | Simulation with data-based inputs | Needs Phase 4 and 6 outputs | Sensitivity analysis done |
| 8 | Dashboard | Shows only what survived 1-7 | Banner states data span and caveats |
| 9 | Write-up and interview story | The point of the project | README matches the code |
| 10 | Keep collecting, re-run at 30 / 60 / 90 days | More data fixes many limits | Calendar reminders set |

I stop for Vincent's review after the plan, after Phase 1, and after Phase 2. Nothing after Phase 2 starts
without that go-ahead.

## Phase 1: Data integrity audit (the first step)

Goal: answer "what can we do with this data, what can't we, where are the holes, and what do we do about them?"
Output: `docs/data_integrity_report.md`, generated by a script (`src/audit/`) plus SQL, so every number is
reproducible and can be re-run when more data arrives.

### 1A. Completeness: did we capture what we think we captured?
- How many snapshots per day, and how many against the ~144 expected? Where are the missing ones (list every gap over 15 minutes)?
- Does every successful run have station rows, and does every station row belong to a successful run?
- How many stations per snapshot? It was 276 early on and 277 stations have appeared since: when did the extra one appear, is it real, does it have metadata?
- Do stations appear or vanish mid-period (installed / removed / temporarily missing)?
- Are there duplicate rows (same station, same snapshot)? Out-of-order or impossible timestamps?
- Does the folder date (`dt=`) always match the timestamp inside the file? (Matters around midnight and the clock change.)
- Did the file layout or column types change on any day (schema drift)?
- How many nulls per column, per day?
- Daylight saving: Spain moves its clocks on Oct 25, so that local day has 25 hours. Do our hour-of-day and daily counts handle it?

### 1B. Validity: do the values make sense?
- Bikes plus free docks versus the station's capacity: do they add up, how often not, by how much?
- Any negative values, bikes above capacity, mechanical + other not equal to total?
- Do capacity or location change over time for the same station?
- Which combinations of installed / renting / returning occur? What does "installed but not renting" look like (broken? offline?) and how persistent is it?
- Are there stations with permanent oddities (always 0 bikes, always full, never changes)?
- Disabled bikes/docks: how common, do they explain "empty but not really empty"?

### 1C. Freshness and staleness (the biggest known hole)
Known so far: the feed's own timestamp is fresh, but most stations' `last_reported` is more than an hour old at a typical snapshot.
- What share of stations is stale by snapshot, by hour of day, by weekday, by station? Is it the same stations every time?
- Suspect to test: `last_reported` only moves when a station sends a message, which may be rare. Does the bike count change while `last_reported` does not? If yes, `last_reported` is not a reliable "is this number current" signal, and the staleness flag over-flags.
- Conversely, does the count ever stay frozen for days at a station that is "fresh"?
- How many stations never change their count at all over the whole period? What share of all changes come from the top 10% of stations?
- Does the stale share depend on the time-of-day cutoff (30 min, 1 h, 3 h)? Test how sensitive every later number is to this threshold.
- Does the feed's `last_updated` timestamp keep moving, or does the feed sometimes serve a cached copy (repeated identical snapshots)? Count identical consecutive snapshots.

### 1D. Is there enough signal and resolution?
- How often does a station's count change between consecutive 10-minute snapshots? Distribution per station.
- How long do stockouts last compared to the 10-minute spacing? (If most last under 10 minutes, we are under-sampling them.)
- How many stockout and blockout events exist in total, per station, per hour? Is the event rate high enough to model (class imbalance), or so rare that most stations have almost none?
- Are many "stockouts" long-lasting structural ones (a station that is always empty), which is a different story from transient ones?
- Are the big upward jumps in a station's bike count at quiet hours likely truck rebalancing? (Hypothesis only; we have no truck data. This matters for the simulation.)
- Inferred activity is a lower bound on trips: how much could we be missing at this sampling rate?

### 1E. Weather
- Coverage and nulls in the weather fields. It is one city-wide reading, updated hourly at best: how much does it actually vary across the period? Were there rain days at all?

### 1F. Time coverage and calendar problems
- 15 days is about two weekly cycles. How many of each weekday do we have (two of each)? How many weekends?
- Spanish public holidays inside the window (to check: Oct 9 regional day, Oct 12 national day) may make some days atypical. Flag them rather than assume.
- One autumn month only: no summer, no school holidays, no festivals (e.g. Fallas), no seasonal comparisons possible.
- The first day (Oct 9) is partial and collected under the old schedule; decide whether to exclude it.

### 1G. Does our own modeling layer tell the truth?
- Reconcile: row counts and stockout counts from raw parquet versus `fct_station_snapshot`, `fct_station_hour` and the KPI mart. They must match exactly.
- Spot-check 20 random station-hours by hand against raw rows.
- Do the dbt tests pass on the real data (not just the synthetic sample)? Add tests that only make sense on real data (e.g. bikes <= capacity).
- Does the staleness flag, activity definition and gap rule behave sensibly on real data?

### 1H. Deliverables of Phase 1
1. `docs/data_integrity_report.md`: findings with the number behind each.
2. A **can / can't / only-with-caveats table** for every analysis in the project (see Phase 2).
3. A **holes register**: each problem, how big it is, what we do about it (flag, exclude, restrict, reframe, collect more).
4. A short list of new dbt tests and checks to keep running as data grows.

### Ways we can respond to a hole (decided per finding)
- **Flag it** and carry the flag into every result.
- **Exclude** the affected rows and state how many were dropped.
- **Restrict** the analysis to the trustworthy subset (e.g. only stations with reliable updates).
- **Report two versions** (all data versus trustworthy subset) so the reader sees the sensitivity.
- **Reframe the question** to one the data can answer.
- **Collect more** (more days, or an extra field) when time is the only fix.
- We do **not** silently fill gaps with guesses.

## Phase 2: Analysis charter
For each planned analysis, one of three verdicts, with the audit finding that justifies it:
- **Can do**, **can do with stated caveats**, or **cannot do (yet)**.

Likely candidates to classify (the audit decides, these are not conclusions):
| Analysis | Main question the audit must answer |
|---|---|
| Availability patterns by hour and weekday | Is the count trustworthy enough, and for which stations? |
| Stockout / blockout rates | Are stockouts real or stale readings? |
| Station segmentation (ABC/XYZ) | Is inferred activity stable and meaningful with this staleness? |
| Short-horizon stockout forecast | Are there enough events, and is the label observable? |
| Rebalancing simulation | Can any parameter be estimated from data, or is it all assumption? |
| Weather effect | Was there enough variation in weather to see any effect? |
| Seasonality, holidays, events | Almost certainly "cannot do yet" |
| True demand / trips / revenue | Cannot do: no trip data (lower bound only) |
| Effect of real-world rebalancing | Cannot do: no truck data |

## Phase 3: Fix the data layer to match reality
- Revisit the staleness rule using Phase 1 results (keep 1 hour, change it, or replace it with something better).
- Add exclusion/flag columns the audit calls for; keep rules in `dbt_project.yml` so thresholds are visible and changeable.
- Add real-data tests. Keep CI on synthetic data; run the real-data checks locally and in the daily health check.
- Rebuild the tables on the frozen dataset and re-reconcile.

## Phase 4: Descriptive service-level analysis
- Stockout and blockout rates by station, hour and weekday, with data-coverage columns and an "all data vs trustworthy subset" comparison.
- Map-ready table by station. Identify persistently problematic stations versus peak-hour problems.
- Every chart says how many days it is based on.

## Phase 5: Segmentation
- Re-run ABC/XYZ on real data; test stability: split the period in half, and perturb thresholds, and report how many stations change class.
- Document that activity is a lower bound.

## Phase 6: Forecasting (only if Phase 2 allows)
- Fix the target definition from Phase 1 (what exactly counts as a stockout, how stale readings are treated, horizon).
- Time-ordered backtest only (never random splits), baselines first, then the gradient-boosted model.
- With about 2 weeks, expect few folds: report scores with uncertainty intervals, per-station-group results, and calibration.
- Honest outcomes allowed: "the model beats the baselines by X", "no better than the hour-of-week average", or "not enough events to say".

## Phase 7: Simulation with data-based inputs
- Replace made-up demand parameters with ones estimated from the data wherever Phase 1 says they can be; keep the rest labelled as assumptions.
- Add a sensitivity analysis: which assumptions change the answer most?
- Present the output as "how policies compare under these assumptions", never as a prediction of real savings.

## Phase 8: Dashboard
- Built only from tables that survived Phases 3-7. Banner shows data span, cutoff, and the main caveats.
- Test locally first. Publishing anything public needs Vincent's explicit ask (rule 5 in CLAUDE.md).

## Phase 9: Write-up and interview story
- README and a short case-study page: question, data and its holes, method, results with uncertainty, what was learned, what would be done with more data.
- A one-page "how I'd explain this" script for interviews, including the staleness story and why results are modest if they are.

## Risks and open questions
- Staleness may turn out to make the bike counts far less informative than they look. If so, the project's honest finding is about data limits, and that is still a strong story if handled well.
- 15 days may be too little for forecasting claims. The plan allows for "inconclusive".
- GitHub or Cloudflare could change terms or limits; the daily health check is the safety net.
- Open: do we want a Quarto report for Phase 1 (Vincent knows Quarto)? Default: markdown generated by Python for now; can be converted later.
